# Localhost Discord Web v1 架構設計

> **狀態：已確認設計、尚未實作。**
>
> 本文件只定義 DiscordBOT Web v1 的範圍與架構。本輪不建立網站、不安裝套件，也不修改 Python、資料庫、測試、GitHub Actions、Token、備份或使用者資料。後續實作必須先由使用者檢閱本文件，再另行建立實作計畫。

## 1. 目標與邊界

Web v1 是僅供本人在本機使用的生活記帳網站，僅監聽 `localhost` 的 `127.0.0.1`；不開放區域網路或外網。網站與 Discord Bot 共用同一份既有生活記帳資料，讓本人可用網頁讀寫帳務。

產品優先順序固定如下：

1. 快速記帳。
2. 清楚查詢與月曆。
3. 基本設定。

Web v1 明確不納入下列範圍：

- React、原生 App 或其他 App 方案。
- 投資、AI、固定支出。
- 匯出、備份、還原。
- 儲蓄目標、日預算、週預算。
- 首頁小工具自訂。
- 訪客或不對應 Discord 帳號的本機模式。

固定支出只保留為未來設定頁規劃，Web v1 不提供讀取、設定或寫入。

## 2. 技術方向與帳務邊界

Web v1 預定使用 FastAPI、伺服器直接產生 HTML 頁面，以及少量只處理頁面互動的 JavaScript。它不是完整 JSON API；不建立公開或前端專用的 REST API。

不導入 React、SQLModel、Alembic、Repository 模式、依賴注入容器或微服務。保留現有 SQLite、交易、rollback、revision 與使用者隔離規則。

預定 Web 模組結構如下：

```text
web/
├── app.py          # FastAPI 建立、localhost 啟動設定與共用 Web 設定
├── auth.py         # Discord OAuth、Cookie 登入狀態、登出與登入保護
├── routes.py       # HTML 頁面與表單路由
├── templates/      # 伺服器產生的 HTML 範本
└── static/         # CSS 與少量瀏覽器端 JavaScript
```

帳務呼叫方向固定為：

```text
Web route → 已驗證 Discord user_id → life_ledger_service.py → spending.py → SQLite
```

Web route 只能使用 OAuth 驗證後的 Discord `user_id`。不得直接 SQL，不得讓前端以網址、表單、Cookie 以外的自訂值或 query parameter 傳入、覆寫或指定 `user_id`。

`life_ledger_service.py` 持續是生活帳務的唯一入口，並繼續委派既有 `spending.py` 規則。若 Web v1 所需能力尚未存在，只新增最小的 Services 方法；不得由 Web 直接繞過 Services，也不得藉此重構為新的資料存取架構。

## 3. 身份與安全

### 3.1 登入與帳號對應

- 使用 Discord OAuth 登入。
- OAuth 成功後，只使用 Discord 驗證回傳的 Discord ID，對應既有 Bot 的同一使用者資料。
- 不提供訪客登入、本機臨時帳號或手動輸入 Discord ID。
- 登入狀態以安全 Cookie 保存 7 天，並提供登出；登出後該 Cookie 不可再用於讀寫帳務。
- OAuth Client ID、Client Secret 與回呼網址只可放在 `.env`。程式、Git 與文件範例不得含真實值、Token 或 Secret。
- OAuth 回呼網址預定為 `localhost` 位址，並與實際 `.env` 設定一致。

### 3.2 請求保護與錯誤處理

- 所有讀取與寫入帳務的頁面或表單都必須先驗證登入狀態；未登入者不可讀取或寫入任何帳務資料。
- 所有寫入表單必須具備 CSRF 防護；缺少、過期或不符的 CSRF 值不得寫入資料。
- 伺服器只監聽 `127.0.0.1`，不可綁定 `0.0.0.0`、區域網路位址或外網位址。
- 使用者不得透過網址、表單或 query parameter 指定或存取其他 Discord ID；每個 Services 呼叫皆使用目前已驗證登入狀態的 ID。
- 對使用者顯示的錯誤訊息只說明可採取的動作，不得暴露 SQL、檔案路徑、Token、Cookie 內容或內部例外。

## 4. Web v1 頁面與互動

### 4.1 首頁

首頁上方顯示頁面標題與搜尋入口。中央直接顯示快速記帳表單，不需先按「新增」按鈕或開啟彈窗。

快速記帳表單欄位與儲存行為如下：

| 欄位 | 行為 |
| --- | --- |
| 金額 | 必填。沿用生活帳務既有金額驗證。 |
| 用途 | 文字輸入。沿用生活帳務既有用途驗證。 |
| 分類 | 可略過；略過時使用「未分類」。 |
| 付款方式 | 自動帶入此已登入使用者上次使用的選項；若尚無上次選項，保持未選擇。 |
| 日期 | 預設今天，可由日期選擇器手動修改。 |
| 儲存 | 直接新增一筆 `consumption` 消費。 |

表單下方並列兩張卡片，左右之間保留明顯間距：

- **本月預算摘要：** 顯示本月預算、已消費與剩餘或超支狀態。
- **本月曆預覽：** 只以每日是否有記帳的小記號呈現，不在日期格內顯示金額。

首頁應提供「查看月曆」入口。若尚未有分類、付款方式或本月預算，對應卡片下方顯示可前往設定頁的非阻擋提示卡；使用者仍可直接新增消費，不能因設定不完整而被擋住。

### 4.2 搜尋

搜尋頁或搜尋入口提供下列條件：用途關鍵字、起始日期、結束日期。

- 至少填寫「關鍵字」或「起始日期」其中一項。
- 只填關鍵字時，搜尋所有日期。
- 只填起始日期時，搜尋起始日至今天。
- 同時填起始與結束日期時，搜尋指定區間。
- 關鍵字可與日期條件同時套用。
- 結束日期不得單獨使用；此情況顯示安全的表單驗證訊息，且不執行查詢。
- 網頁一律使用日期選擇器；不沿用 Discord 指令的多種文字日期格式。

搜尋結果僅可包含目前已登入 Discord 使用者的有效 `consumption` 消費。

### 4.3 完整月曆頁

由首頁月曆卡或「查看月曆」按鈕進入完整月曆分頁；首頁不使用半透明彈窗承載完整月曆。

- 日期格在未點選時只顯示是否有記帳，不顯示金額。
- 點選日期後，才顯示當日總金額與該日消費明細。
- 桌機與手機版都必須有足夠大的日期觸控／點擊區域。
- 月曆資料與當日明細皆只讀取目前已登入使用者資料。

### 4.4 設定頁

Web v1 設定頁只包含：

- 本月總預算設定。
- 分類新增、修改、停用或刪除。
- 付款方式新增、修改、停用或刪除。

固定支出屬於未來設定頁規劃，Web v1 不顯示或實作。

設定頁的每項讀寫都使用已驗證 Discord `user_id` 與 CSRF 防護；不能用路由參數、表單欄位或 query parameter 操作其他使用者的分類、付款方式或預算。

## 5. 預定最小整合原則

- HTML route 負責登入檢查、CSRF 驗證、表單資料轉換、呼叫 Services 與呈現安全訊息。
- `auth.py` 負責 OAuth 與 Cookie 狀態；它不執行 SQL，也不處理帳務規則。
- `routes.py` 不複製金額、日期、分類、付款方式、交易、rollback、revision 或使用者隔離規則。
- 現有 `life_ledger_service.py` 優先使用既有新增、搜尋、月曆、月摘要、分類與付款方式能力。只有設定頁或首頁確實缺少的最小帳務能力，才在後續核准的實作中補入 Services。
- Web v1 不建立 JSON API。少量 JavaScript 僅可用於已產生 HTML 的互動，例如月曆日期點選；帳務授權與驗證仍在伺服器端。

## 6. 測試與驗證方向

後續實作時，所有 Web 測試都必須使用隔離資料庫，絕不接觸正式 `data.db`。OAuth 必須使用測試替身，不連線真實 Discord。

最低測試範圍如下：

- 未登入保護、使用者隔離、CSRF、登入逾期與登出。
- 快速新增消費、搜尋、完整月曆與首頁預覽的基本流程。
- 本月預算、分類與付款方式的基本設定流程。
- 搜尋條件規則：至少一個必要條件、結束日期不可單獨使用，以及關鍵字與日期可同時套用。
- 同一筆或同一日期資料不得跨 Discord 使用者讀取或寫入。
- OAuth 測試替身驗證登入後的 Discord ID 對應，不連線真實 Discord。

既有驗證必須保留：

```powershell
python -m ruff check .
python tests/run_discord_validation.py
```

下列事項即使未來測試通過，仍必須明確標示為另行驗證，不能宣稱已由此設計或自動測試驗證：

- 真實 Discord OAuth。
- 真實 Discord UI。
- 正式資料庫升級。
- 外網部署。
- 手機實機互動。
